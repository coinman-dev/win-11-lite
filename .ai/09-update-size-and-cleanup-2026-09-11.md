# Рост ISO после обновлений — 11.09.2026

## Что установлено

В текущем коде порядок LCU → удаления → StartComponentCleanup → экспорт в новый ESD уже был правильным. Скачанные MSU находятся в отдельном кэше, а не копируются внутрь ISO. WIM после commit может содержать старые данные; итоговый экспорт в новый файл уже выполнялся, поэтому отсутствие переэкспорта не является найденной причиной.

В историческом отчёте 06 зафиксированы ISO 4.69 ГиБ и install.esd 3.94 ГиБ после обновлений. Полного лога этого прогона сейчас в `log` нет. Доступные прогоны `214252` и `220239` выполнены с `UpdateMode=none`, с повторным применением исходного LCU для языка. Они не воспроизводят интеграцию последнего LCU. Точную долю устранимого раздувания по этим данным определить нельзя.

Прежние выводы «WinSxS вырос на 3.5 ГБ даже после ResetBase» недостаточно обоснованы: размеры были получены сложением Length, без учёта hard links. Удаление одного имени файла также не освобождает его содержимое, если оно осталось доступно через другие имена. Размеры удалённых файлов не равны экономии ESD/ISO. [Как Microsoft измеряет WinSxS](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/determine-the-actual-size-of-the-winsxs-folder).

Обновления действительно добавляют новые версии компонентов, а CBS сохраняет нужные рабочие файлы, зависимости и данные обслуживания. Операция удаления пакета сама по себе не обещает уменьшения offline-образа: нужны очистка и экспорт. Часть действий может остаться в состоянии `Install Pending` до загрузки Windows. [Ограничения DISM](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism-operating-system-package-servicing-command-line-options).

## Исправления в balanced

1. Возможности и пакеты со статусом `Staged` теперь тоже обрабатываются по действующим правилам удаления. Раньше выбирались исключительно `Installed`. Статусы `Install Pending` / `Uninstall Pending` выводятся явно и не считаются успешным удалением. Незавершённое обслуживание требует загрузки Windows; commit/remount её не заменяют.
2. Recall обрабатывается через `/Get-Features`, затем `/Disable-Feature /FeatureName:Recall /Remove`, если функция существует и не ожидает завершения операции. Учитывается `-Keep AI`. Раньше были только политики и удаление отдельных каталогов. Проверяется итоговое состояние; `Disabled` не приравнивается к `Disabled with Payload Removed`. [Управление Recall](https://learn.microsoft.com/en-us/windows/client-management/manage-recall).
3. После последнего обслуживания DISM повторяются действующие файловые удаления и проверка отсутствия Edge. Проверка WebView2 теперь допускает смену каталога версии после обновления, но требует наличия runtime в защищённых каталогах.
4. После очистки повторно запрашиваются capabilities, packages, provisioned Appx и optional features. В итоговом отчёте видны оставшиеся выбранные компоненты и состояния, включая pending.
5. Отказы удаления пакетов и Appx больше не скрываются в Verbose: выводятся код HRESULT и текст DISM, сохраняемые в отчёте. Например, присутствующий в доступном логе отказ Sense — это отказ обслуживания, а не успешное удаление пакета; отдельная файловая очистка не меняет этот факт.

Состав и порядок удаления `max` сохранены. Новые обработка Recall, выбор Staged и повторная файловая очистка включены только для `balanced`. Общая диагностика ошибок стала подробнее на обоих языках.

## Измерения следующего прогона

Для balanced вызывается `/AnalyzeComponentStore` в трёх точках: `source`, `after-integration`, `after-cleanup`. Отчёт показывает фактический размер, общие с Windows файлы, резервные копии/отключённые функции, временные данные и число пакетов для очистки. Отказ необязательного анализа не прерывает сборку и не выдаётся за нулевой размер.

Рядом с выходным ISO сохраняется `<имя>.image-audit.json`. Он содержит исходные ответы анализа DISM, отказы удаления, итоговый список оставшихся компонентов и, после успешного завершения, размеры исходного и готового ISO. Сравнивать два ISO нужно при одинаковых Index, языках, пресете, WinRE, TrimSources и Compression, меняя только интеграцию LCU. Иначе разницу нельзя приписать одним обновлениям.

`ResetBase` автоматически не включён. Уточнены слишком категоричные прежние сообщения: документированное последствие — невозможность удалить уже установленные обновления; утверждение, что он всегда ломает будущие LCU на любом 26100+, не доказано этим проектом. Для checkpoint-медиа остаётся штатная последовательность с StartComponentCleanup. [Процедура Microsoft](https://learn.microsoft.com/en-us/windows/deployment/update/catalog-checkpoint-cumulative-updates), [очистка offline-образа](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/reduce-the-size-of-the-component-store-in-an-offline-windows-image).

## Проверки и ограничения

90 проверок прошли на PowerShell 7.6.6 и Windows PowerShell 5.1.19041.7725. Новые сценарии: Staged/Pending, защита языкового Basic и Keep, полный текст ошибок, состояние Recall, восстановление Edge во время DISM cleanup и его удаление до commit, обновлённый WebView2, сохранение JSON, сбой необязательного анализа. Обслуживание образа в тестах подменено; системные настройки хоста не менялись.

DryRun balanced с `-WithUpdates -DownloadLanguage ru-RU` прошёл. Реальное обслуживание с последним LCU, сжатие и установка ISO этой редакции не выполнялись: процесс проверки без прав администратора. Количество сэкономленных мегабайт не заявляется до замера.
