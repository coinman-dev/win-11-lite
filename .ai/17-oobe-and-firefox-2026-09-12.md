# Повторные обновления OOBE и удаление Install-Firefox

Пользователь показал OOBE с проверкой обновлений и скачиванием на 1 %, затем рабочий стол VM, журнал guard (57 проверено, 0 изменений, 0 ошибок) и работающий Firefox. Попросил вернуть установку без обновлений и удалять одноразовый ярлык после успешной установки Firefox.

## Подтверждённые данные

- Восстановленные журналы находятся в `log/old`, `log/old2`, `log/old3`. Последний из них — `...20260912-160744.log`: ID сборки 20260912-160701, завершение 17:53:23, в плане сеть для OOBE должна быть выключена.
- Текущий ISO в out имеет размер **3 155 714 048 байт**, дату 18:55:55 и встроенный ID **20260912-180510**. Windows/Setup ru-RU, UpdateMode none, WithWinget false, Guard/GuardDebug true, пропущенных загрузок нет. SetupLanguageUpdate — KB5043080.
- Из текущего ISO прочитаны autounattend.xml, Prepare.ps1, Finalize.ps1 и SetupComplete.cmd. Блокировка сети включена, вызов Prepare присутствует в specialize; SetupComplete вызывает Prepare с RegisterOnly. Это не доказательство выполнения этих действий внутри VM.
- Гостевых prepare.log/finalize.log в восстановленных папках нет. Пользователю отправлен запрос их текста. Управление Hyper-V из текущего сеанса недоступно из-за прав; гостевой ID сборки не прочитан. Не считать автоматически доказанным совпадение текущего ISO с запущенной VM и не возобновлять старую гипотезу об ISO на E: без новых данных.

## Найденные недостатки и изменения

1. Старый Prepare проверял список адаптеров один раз. Пустой список считался успешным отключением. Новый код повторяет обнаружение до 15 попыток и явно сообщает о недоступности адаптеров.
2. RegisterOnly в SetupComplete раньше пропускал блокировку сети. Теперь он повторяет её, подхватывая поздние адаптеры и интерфейсы, повторно включённые PnP.
3. Временное правило `Win11Lite-OOBE-Temporary-Outbound-Block` (PersistentStore, Outbound, Block, Any profile) защищает и будущие интерфейсы. Без доступных адаптеров и без успешной установки правила подготовка не сообщает, что сеть изолирована. Отключение адаптеров остаётся независимым от регистрации задач.
4. Старый Finalize с FirstLogon полностью обходил проверку состояния OOBE. Теперь используется документированный Kernel32 `OOBEComplete(out BOOL)`; само событие входа не разрешает включать сеть. При раннем FirstLogon запускается скрытый ожидающий процесс, а FirstLogonCommands возвращает управление. SYSTEM-задача тоже получает WaitForOobe. Таймаут ожидания 2 часа, предел задачи 3 часа; при таймауте задача сохраняется для следующего входа.
5. Ошибка запроса OOBE означает неизвестное состояние и повторную проверку, а не разрешение на включение сети. После подтверждения создаётся маркер oobe-complete, предотвращающий повторную блокировку поздним SetupComplete.
6. Снятие собственного правила, восстановление сохранённых адаптеров и временных политик выполняются независимо. Отказ Edge или адаптера не препятствует попытке удалить сетевой блок; ошибки сохраняют задачу повторного запуска.
7. В prepare/finalize добавлены режим вызова, пользователь, GUID адаптеров, ожидание OOBE и возврат сети. В build-info — OobeNetworkBlock и OobeCompletionCheck. Диагностический сборщик дополнен адаптерами, сохранёнными GUID, маркером, сетевым правилом и политиками.

Эти недостатки воспроизведены тестами. **Без гостевых журналов нельзя установить, какой именно сценарий вызвал обновления на скриншотах. Новое поведение в VM ещё не проверено.**

Одна политика AllowOOBEUpdates не использована как решение: документация Microsoft прямо исключает из её действия страницу ZDP и на проверенной странице ограничивает применимость Insider Preview. Сетевой блок не зависит от этой политики.

## Firefox

Общий выход после успешного winget/установщика удаляет именно запущенный Install-Firefox.cmd. На ошибке скачивания/отмене/ненулевом коде установщика файл остаётся. Удаление CMD с последующим `exit /b` вызывало `The batch file cannot be found`; проверенный вариант `(goto) 2>nul & del /f /q "%~f0" >nul 2>&1` завершает batch-контекст до удаления.

Успех winget теперь означает ровно код 0. Прежнее `if not errorlevel 1` принимало отрицательные HRESULT за успех; новые проверки покрывают отрицательный код winget с успешным и неудачным прямым скачиванием.

Write-FirefoxInstallerFile сохраняет прежний UTF-8 без BOM + CRLF и даёт Users право Delete только на этот файл. Это позволяет удалить ярлык с общего рабочего стола без дополнительного UAC. Запись/изменение файла обычным пользователям не разрешаются. Обычный Firefox.lnk не удаляется. Проверены пути с пробелами, кириллицей, `&` и `!`.

## Проверки

На PowerShell 7.6.6 и Windows PowerShell 5.1.19041.7725 прошли: Main 130, CMD 142, Guard 33, Downloads 80, SetupLanguage 54, OobeNetwork 40 — **479 на каждой версии**. Итоговые логи — `.ai/oobe-validation`.

- OOBE-тесты полностью подменяют сетевые, firewall, task, process и native OOBE API. Покрывают поздние/вновь включённые интерфейсы, повторный SetupComplete, ранний первый вход, временного пользователя, ожидание/таймаут/недоступный API, независимое восстановление при сбоях, EdgeOnly и отключение управления сетью.
- CMD-тесты запускают настоящий cmd.exe с заглушками загрузок/установщиков и проверяют наличие файла после каждого исхода, ACL и сохранение Firefox.lnk.
- Отдельно вызван только read-only API OOBEComplete на хосте: привязка Kernel32 работает и возвращает true. Prepare/Finalize/guard на хосте не запускались.
- В тестах Add-Type для 5.1 компилирует заглушку в собственном временном каталоге: системный C:\Windows\TEMP в этом сеансе дал ошибку чтения временного C#-файла. Это изменение тестовой среды, не реальное подтверждение API внутри VM.
- Существующий ISO и работающая VM не изменялись. Для проверки исправлений нужна новая сборка; гостевые журналы старой установки всё ещё нужны для точной диагностики.

Резервная копия: `.ai/win-11-lite.before-oobe-firefox-20260912.ps1`. Извлечённые материалы ISO — `tmp/oobe-regression-20260912`; большая временная копия install.esd сохранена после отказа автоматической проверки разрешить её удаление, исходный ISO не затронут.
