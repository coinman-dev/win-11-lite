## 2026-09-27

### oscdimg без установки ADK

- Реальная сборка через мастер на хосте без ADK остановилась на стадии 4: «Нужны DISM build 19041 или новее и oscdimg… используйте -InstallAdk». При этом системный DISM (10.0.26100) подходил, не хватало только `oscdimg`, а мастер ключ `-InstallAdk` не предлагает.
- Теперь в таком случае `Initialize-DeploymentTools` берёт `oscdimg` из того же закреплённого набора пакетов Microsoft ADK, что и для 26H1: 4 установщика и 9 архивов, SHA256 архивов, размеры из таблиц MSI, проверка подписи, кэш. ADK не устанавливается, DISM остаётся прежним. `oscdimg` от ветки Windows не зависит. DryRun заранее сообщает о подготовке. Явный `-InstallAdk` по-прежнему ставит Deployment Tools, `-SkipIso` обходится без `oscdimg`. При сбое загрузки сохраняется причина и подсказка про `-InstallAdk`.
- Проверено настоящей подготовкой на этом хосте для Windows 10 (19041): 20,5 с, `oscdimg` 2.56.0.1010 с действительной подписью Microsoft Corporation, DISM — системный 10.0.26100.8972; повторный вызов из кэша — 1,1 с. DryRun ISO Windows 10 показывает новое сообщение.
- Servicing 190 → 196: только `oscdimg` при своём DISM, DryRun без загрузок, `-InstallAdk`, `-SkipIso`, причина сбоя. Все 14 наборов, 1430 проверок, прошли на Windows PowerShell 5.1.

### Мастер неверно читал ISO с одной редакцией

- Реальный запуск мастера на `ru-ru_windows_10_iot_enterprise_ltsc_2021_x64_dvd_5044a1e7.iso` (одна редакция) показал «Образ на языке en-US», задал вопрос о добавлении языка как для Windows 11 и после ответа остановился: «Добавление языков для Windows 10 не поддерживается».
- Причина: `Get-IsoEditions` при одной редакции возвращает одиночный `PSCustomObject`, а у него в Windows PowerShell 5.1 нет `Count`. Поэтому не срабатывали ни ветка «одна редакция», ни меню редакций: индекс оставался 0, язык — значение по умолчанию `en-US`, семейство Windows не определялось, а вопрос об учётной записи пропускался. Ошибка давняя, она затрагивает любой ISO с одной редакцией в PS 5.1.
- Исправление: `$editions = @(Get-IsoEditions …)`. После него мастер на том же ISO сообщает «В образе одна редакция: Windows 10 Enterprise LTSC 2021», не спрашивает о языке, показывает размер обновления для Windows 10 и снова спрашивает об учётной записи. Проверено воспроизведением настоящего мастера на реальном ISO (подменены только ввод и проверка winget).
- Servicing 188 → 190: настоящий участок мастера с одной и с двумя редакциями. Отдельно подтверждено, что без `@()` тот же участок даёт индекс 0, en-US и не-Windows 10. Все 14 наборов, 1424 проверки, прошли на Windows PowerShell 5.1.

### Удаление компонентов виртуализации (`-RemoveVirtualization`, вопрос мастера)

- Новая группа `Virtualization` в таблице `FeatureRules` (компоненты Windows из `DISM /Get-Features`): Hyper-V с Диспетчером Hyper-V (`Microsoft-Hyper-V*`), WSL и платформа виртуальных машин (`Microsoft-Windows-Subsystem-Linux`, `VirtualMachinePlatform`), `HypervisorPlatform`, песочница и контейнеры (`Containers`, `Containers-DisposableClientVM`), `Windows-Defender-ApplicationGuard`. Компоненты удаляются вместе с файлами (`/Disable-Feature /Remove`) на новой стадии после удаления возможностей Windows. Уже удалённые пропускаются, незавершённое обслуживание откладывается, ошибка DISM записывается и не останавливает следующий компонент.
- Группа входит в `max`. В `safe`/`balanced` она удаляется только с новым ключом `-RemoveVirtualization`, а в `max` её сохраняет `-Keep Virtualization`; оба ключа вместе дают ошибку. Это сознательное расширение `max` по решению пользователя; `balanced` по умолчанию по-прежнему сохраняет Hyper-V и WSL.
- Мастер после вопроса об антивирусе спрашивает «Удалить компоненты виртуализации?»: по умолчанию «нет», для `max` — «да». Жёлтое предупреждение: удаляйте, только если не будете пользоваться виртуализацией, иначе не работают WSL, Docker Desktop, виртуальные машины Hyper-V и песочница. «Да» вне `max` — это `-RemoveVirtualization`, «нет» в `max` — `-Keep Virtualization`.
- В плане сборки появилась строка «Виртуализация» и предупреждение о том, что без исходного образа компоненты уже не включить. Отчёт об оставшихся компонентах (balanced) учитывает и эти правила.
- Не затрагиваются: гостевые интеграционные службы Hyper-V, с которыми сама Windows работает внутри VM (часть ядра), и гипервизор VBS (в Windows Home компонентов Hyper-V нет, а VBS работает). Guard эти компоненты не отслеживает. `-Keep Sandbox` по-прежнему ни на что не влияет: песочница сохраняется через `-Keep Virtualization`.
- Compatibility 170 → 209:
  - принадлежность 13 имён компонентов правилам и отсутствие ложных совпадений;
  - пресеты и ключи;
  - удаление с подменённым DISM (включая уже удалённые, pending, ошибку и отсутствие запросов без группы);
  - настоящий блок мастера для всех пресетов и ответов на RU/EN;
  - конфликт ключей.
- DryRun ISO Windows 10: `balanced`, `max`, `max -Keep Virtualization`, `-RemoveVirtualization`, отказ при конфликте. Все 14 наборов, 1412 проверок, прошли на Windows PowerShell 5.1. Реального удаления в образе и установки в VM не было.

### Вопрос мастера: удалять ли встроенный антивирус

- Для `balanced` и `max` мастер сразу после выбора пресета спрашивает «Удалить встроенный антивирус?». Ответ по умолчанию — да. Перед вопросом жёлтое предупреждение: удаляйте, только если будете устанавливать другой антивирус, иначе Windows останется без защиты от вредоносных программ. Для `safe` вопроса нет: там Defender не удаляется.
- Ответ «нет» добавляет `Defender` в `-Keep`. Сохраняются Defender, «Безопасность Windows», их службы и политики; Guard их не проверяет; итоговая команда мастера содержит `-Keep Defender`. Если `-Keep Defender` уже задан, он становится ответом по умолчанию, а «да» убирает из `-Keep` только эту группу.
- Compatibility 164 → 170: настоящий блок мастера для `safe`/`balanced`/`max`, ответов по умолчанию, «нет» и «да» при заданном `-Keep`, текстов RU/EN. DryRun ISO Windows 10 с `-Keep Defender` показывает «Не трогаем: Defender». Все 14 наборов, 1373 проверки, прошли на Windows PowerShell 5.1.

### Автоматическая установка без вопросов (`-AutoInstall`)

- Новый ключ `-AutoInstall` собирает носитель, который ставит Windows без вопросов установщика и OOBE, а затем выполняет автовход. Мастер спрашивает об этом сразу после выбора редакции (по умолчанию — нет). В плане сборки появилась строка «Установка»; предупреждение о диске выводится в плане и повторяется в итоговом отчёте.
- **Диск 0 стирается без подтверждения.** Команда `RunSynchronous` в проходе windowsPE ищет `win11lite\disk.cmd` на всех буквах носителя, кроме X:. Сценарий определяет прошивку по `PEFirmwareType` (разбор через `for /f`, без зависимости от `find`) и запускает `diskpart`: для UEFI — GPT (ESP 300 МБ, MSR 16 МБ, Windows), для BIOS — MBR (активный System Reserved 300 МБ, Windows). Раздел выбирает `InstallToAvailablePartition`, потому что номер раздела Windows у GPT и MBR разный. `RunSynchronous` стоит между `ImageInstall` и `UserData`, как требует порядок схемы.
- Вход по умолчанию — встроенный Администратор с пустым паролем: `AutoLogon` с языконезависимым именем `Administrator`, который по документации Microsoft включает учётную запись на любом языке образа, плюс пустой `AdministratorPassword`. При настроенном `AutoLogon` Windows 10+ пропускает создание пользователя в OOBE. С `-LocalUserName` создаётся и входит этот администратор; его пароль в `AutoLogon` кодируется так же, как в `LocalAccount`. `LogonCount` — 9999999.
- Для `-AutoInstall` UEFI грузится с `efisys_noprompt.bin`: иначе без нажатия клавиши прошивка пропустила бы DVD. Файл есть на ISO Windows 10 LTSC 2021 и Windows 11 LTSC 2024; при его отсутствии выводится предупреждение и остаётся обычный `efisys.bin`.
- Home/Pro без `-ProductKey` останавливаются до загрузок (в мастере ключ запрашивается). Несовместимые сочетания: `-Unattend` (любой) и `-AccountMode setup`. В `build-info.json` добавлены `AutoInstall` и `AutoLogon`.
- Servicing 151 → 178:
  - настоящие выражения answer-файла: порядок элементов, `InstallToAvailablePartition` без `InstallTo`, `AutoLogon`/`AdministratorPassword`, именованная учётная запись;
  - выбор загрузочного образа;
  - запуск настоящим `cmd.exe` той же командной строки, что в answer-файле, через `subst`-носитель, с подменёнными `reg`/`diskpart` и безвредными сценариями-заглушками; перед запуском тест проверяет, что `where diskpart` находит фикстуру.
- Compatibility 155 → 164: ключ для Home/Pro и конфликт с `-Unattend`. DryRun на ISO Windows 10 LTSC 2021: встроенный Администратор (RU), `-LocalUserName` (EN), отказы `-AccountMode setup` и `-Unattend none`. Все 14 наборов, 1367 проверок, прошли на Windows PowerShell 5.1. Реальной автоматической установки в VM ещё не было.

### Поддержка Windows 10 на базе 19041 (2004–22H2, LTSC 2021)

- Раньше сборщик останавливался на стадии 3 с «Неизвестная ветка Windows: 19041». В XML носителя Windows 10 2004–22H2 хранится общий базовый build 19041, а версию задаёт пакет включения: у LTSC 2021 это `10.0.19041.1288`. `Get-WindowsRelease` теперь принимает редакцию. 19041 с `EnterpriseS`/`IoTEnterpriseS` — 21H2 (LTSC 2021), с остальными редакциями — 22H2; 19044 — 21H2, 19045 — 22H2. Ветки 17763 (LTSC 2019), 19042 и 19043 по-прежнему отклоняются.
- Установщик Windows 10 уже классический, а `setup.exe /legacy` есть только в Windows 11. Поэтому для Windows 10 `-LegacySetup` игнорируется с предупреждением, `winpeshl.ini` не пишется, а `-TrimSources` и `-RemoveWinRE` его не требуют. Проверка этих ключей перенесена из preflight на стадию 3, где ветка уже известна; это по-прежнему раньше загрузок, обслуживания образа и очистки рабочего каталога. Для Windows 11 требования не изменились.
- Ключи LabConfig/MoSetup обходят проверки Windows 11, поэтому для Windows 10 они не пишутся ни в реестр образа, ни в `boot.wim`; без других причин `boot.wim` не монтируется.
- Добавление языков (`-AddLanguage`, `-DownloadLanguage`) и смена языка установщика для Windows 10 не поддерживаются и останавливают сборку до любых загрузок. Мастер для Windows 10 не предлагает добавить язык.
- `Get-UpdateCatalogSearch` формирует запросы к каталогу. Для Windows 10 это `Cumulative Update for Windows 10 Version 21H2/22H2 for x64-based Systems` (около 0,9 ГБ, стек обслуживания внутри) и `.NET Framework 3.5 and 4.8`: каталог ежемесячно публикует три варианта .NET, а в образе 19041 стоит .NET 4.8. Официальная процедура Microsoft (media-dynamic-update, август 2026) добавляет объединённый пакет SSU+LCU прямо в образ, поэтому путь интеграции не менялся. Запросы Windows 11 остались прежними. `Save-CatalogPayload` распознаёт любой шаблон .NET, а не только точный `\.NET Framework`.
- Кэш обновлений Windows 10 называется `lcu-win10-<выпуск>`/`dotnet-win10-<выпуск>`: иначе Windows 10 21H2 и Windows 11 21H2 (22000) делили бы одну папку, и при недоступной сети подставилось бы чужое обновление.
- План и мастер для Windows 10: установщик «классический, штатный», обход TPM «не нужен», размер LCU около 0,9 ГБ, строка AI без обещания удалить Recall. Название правила IE уточнено: в Windows 10 Internet Explorer 11 остаётся рабочим браузером. Правила удаления те же, что для Windows 11.
- Проверено на настоящем `ru-ru_windows_10_iot_enterprise_ltsc_2021_x64_dvd_5044a1e7.iso`: DryRun с обычным набором ключей, с `-LegacySetup -TrimSources -RemoveWinRE -SaveWinRE` (RU/EN) и отказ `-DownloadLanguage`. На ISO Windows 11 LTSC 2024 план и отказ `-TrimSources` без `-LegacySetup` не изменились. Выбор каталога проверен настоящим кодом по живому каталогу: Windows 10 21H2 — KB5129236 и .NET KB5126046, Windows 11 24H2 — прежние KB5129195 и KB5126052.
- Compatibility 133 → 155 (ветки Windows 10 и настоящий блок решений по установщику, TPM и языкам), Downloads 82 → 87 (фикстура из реальных названий каталога, где варианты .NET 4.8.1 новее нужного). Все 14 наборов, 1331 проверка, прошли на Windows PowerShell 5.1; PowerShell 7 на этой машине нет. Полной сборки Windows 10 здесь не было: нет прав администратора и ADK. Установка в VM ещё не проверялась.

## 2026-09-17

### Окно отчёта guard исчезало при нечитаемом %TEMP%

- Проверка окончания OOBE компилирует обращение к `OOBEComplete` через `Add-Type`, а тот кладёт исходник в `%TEMP%` и запускает `csc.exe`. Если у профиля нет `HKCU\Environment\TEMP`, сеанс наследует машинный `C:\Windows\TEMP`: обычному пользователю там разрешена запись, но не перечисление каталога, поэтому компилятор не находит только что записанный файл и возвращает CS2001. Такое состояние оставляют сторонние установщики, перезаписывающие `HKCU\Environment` целиком.
- Задача `win-11-lite guard report` выполняется от обычного пользователя и получает окружение из реестра заново, поэтому отказ касался именно её: окно открывалось и закрывалось примерно за секунду с кодом 0, а сам SYSTEM-worker продолжал писать `guard-report.txt/json`, `guard-summary.txt` и дневной журнал.
- `Get-GuestCompilerTempPath` выбирает для компиляции каталог, который не только пишется и читается, но и перечисляется, — то есть повторяет поиск файла компилятором. `%TEMP%` и `%TMP%` подменяются только на время `Add-Type` и возвращаются вызывающему. Порядок проверки: текущий временный каталог, `%LOCALAPPDATA%\Temp`, `%SystemRoot%\Temp`.
- Недоступная проверка OOBE больше не прячет готовый отчёт молча: она опирается на отметку `oobe-complete`, которую пишет финализация, и в любом случае записывает причину отказа в дневной журнал. Признаки идущего OOBE, `defaultuser0` и незавершённой установки по-прежнему проверяются раньше и закрывают окно без обращения к probe.
- GuardModes: 51 проверка на PowerShell 5.1 (+12). Фикстура — настоящий каталог с запретом перечисления для текущего пользователя; проверены выбор пригодного каталога, восстановление `%TEMP%`/`%TMP%`, обе ветки отметки `oobe-complete` и запись причины в журнал. Прошли все 14 наборов, 1304 проверки; PowerShell 7 на этой машине не установлен, на нём наборы не перезапускались. Установленной Windows правка не касается — она применяется при следующей сборке ISO.

### Повторные обновления OOBE и одноразовый ярлык Firefox

- Подготовка повторяет обнаружение адаптеров, а SetupComplete заново проверяет блокировку сети. Временное правило брандмауэра действует и для поздно появившихся интерфейсов.
- Финализатор проверяет системный сигнал OOBEComplete, включая запуск через FirstLogonCommands. До завершения OOBE сеть не восстанавливается; ожидание выполняется скрыто, не удерживая запуск рабочего стола.
- Возврат адаптеров, снятие сетевого правила и восстановление временных политик выполняются независимо. Поздний Prepare не блокирует сеть повторно после завершения OOBE.
- Install-Firefox.cmd удаляет себя после успешной установки через winget или прямой установщик. При ошибке или отмене файл сохраняется. Право удалить только этот одноразовый файл доступно обычным пользователям.
- Успех winget проверяется по точному коду 0: отрицательные HRESULT больше не принимаются за успешную установку.
- Добавлены проверки позднего появления адаптера, раннего первого входа, восстановления сети при сбоях и настоящего самоудаления CMD. Итог: 479 проверок на каждой версии PowerShell; проверка нового поведения в VM ожидается.

### Подготовка загрузок до сборки

- Обновления Windows и .NET, языковые пакеты, winget с лицензией и зависимостями, а также пакеты установщика готовятся до копирования ISO и обслуживания WIM.
- При отказе подготовки пользователь выбирает пропуск компонента или отмену. В неинтерактивном режиме сборка отменяется.
- Полный кэш проверяется по размерам и SHA256; незавершённые файлы `.part` не считаются готовыми. В набор LCU входят checkpoint MSU.
- При отмене сохраняется рабочая папка предыдущей сборки. После подготовки сетевые вызовы не выполняются.

### Язык установщика

- `-SetupLanguage auto` по умолчанию выбирает первый подготовленный язык Windows; `original` сохраняет исходный язык, также можно задать конкретный код языка.
- Добавлен каталог официальных WinPE CAB для build 26100 x64. Поддерживаются локальные источники и кэш; полный WinPE add-on на хост не устанавливается.
- Язык добавляется в индекс 2 `boot.wim`, повторно применяется подходящий LCU, обновляются `lang.ini` и SetupUILanguage. Файлы Setup синхронизируются с носителем.
- `TrimSources` сохраняет языковые ресурсы. Проверка локализации Windows продолжает сравнивать MUI с исходным языком Windows независимо от языка установщика.

### Совместимость и диагностика

- Исправлена обработка stderr нативных утилит на Windows PowerShell 5.1.
- `RemoveWinRE` учитывается при любом пресете; `Keep` сохраняет приоритет.
- Проверка WebView2 учитывает перенос runtime в системный каталог после LCU.
- Индикация прогресса расширена на копирование ISO, обслуживание языков и компонентов, обработку boot.wim и запись ISO.
- Добавлены наборы проверок guard, загрузок и языка установщика. Все итоговые прогоны: 368 проверок на PowerShell 5.1 и столько же на 7.

Реальные входные пакеты и DryRun проверены. Последняя редакция ещё требует полной пересборки ISO и проверки установки в VM.
